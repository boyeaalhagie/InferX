What Is This?

An Inference Performance Engineering System

InferX is a GPU inference performance engineering platform for large language models. Its job is to take a real LLM workload, establish a reproducible performance baseline across multiple runtimes, profile its kernel-level execution on real hardware, identify the limiting hardware resource, and quantitatively evaluate optimization techniques.

Question 1
Why is this engine performing the way it is?
Question 2
What change actually makes it faster?

These are the two questions every result in this project is built to answer. Not "what is the fastest number I can get?" — but a measurement-grounded explanation of the hardware bottleneck and a targeted optimization derived from that explanation.

Not the goal

Knowing that vLLM achieves 8,186 tok/s is not the point. Knowing why PyTorch runs at 81 tok/s at bs=1 — and exactly which hardware constraint each optimization addresses — is the point. A result without an explanation is just a benchmark. An explanation grounded in a measurement is performance engineering.

Experiment B

KV Cache & PagedAttention — vLLM

Standard KV cache allocates contiguous memory per request upfront (max_seq_len × KV bytes). PagedAttention (Kwon et al. 2023) stores KV tensors in fixed 16–32 token blocks, allocated on demand. This eliminates fragmentation and allows more concurrent requests within the same 80 GB HBM budget.

KV Cache Size — Qwen2.5-7B, BF16

2 × 28 layers × 4 KV heads × 128 d_head × seq_len × 2 bytes = 56 KB/token per request.
At seq_len=4096: 229 MB per request. At batch=32: 7.3 GB — significant fraction of 80 GB HBM.

Experiment C

Batching Efficiency — Static vs Continuous

LLM decode at bs=1 is severely memory-bandwidth bound: the full model (15 GB for 7B BF16) must be streamed from HBM for each generated token. Increasing batch size amortizes this cost across more tokens per pass, converting memory-bound GEMV operations into compute-bound GEMM.

ITL is constant across batch sizes (bs=1–32). Decode ITL stays at ~11–12 ms from bs=1 through bs=32, confirming H100 compute is sufficient to process all batch items in parallel. The rise at bs=64 (15.2ms) marks the onset of compute saturation.

Near-linear scaling to bs=32. PyTorch achieves 27× throughput at bs=32 (theoretical max: 32×). The GEMV→GEMM transition is the mechanism: at bs=1, decode GEMMs have arithmetic intensity ~4 FLOP/byte; at bs=32, tiles grow toward compute-bound operation (~128 FLOP/byte).

Experiment D

Latency — Input/Output Length Sensitivity

How does performance change as the workload shifts from short-and-decode-heavy to long-and-prefill-heavy? This experiment varies input and output token counts to characterize which phase dominates.

FINDING D1

vLLM TTFT ratio inverts with prompt length. vLLM is 182× slower on TTFT for short prompts (scheduler overhead dominates) but only 1.9× slower for long prompts (prefill cost dominates, scheduler becomes negligible). Use PyTorch for <256 token prompts with TTFT requirements.

FINDING D2

Long prompts reduce decode throughput. PyTorch throughput drops 26% from in=128 to in=4096 (323→259 tok/s). Longer prefill means more KV cache to attend over during decode, and the prefill phase itself delays decode start.

Experiment E

Precision — BF16, FP16, INT8

Quantization reduces model weight precision to decrease memory bandwidth pressure. For memory-bandwidth-bound decode workloads, narrower dtype → smaller weights → faster HBM streaming. But the actual impact depends on when dequantization happens.

FINDING E1

INT8 saves 45% VRAM with no throughput improvement. bitsandbytes LLM.int8() stores weights as INT8 but dequantizes to BF16 at matrix-multiply time. No bandwidth improvement — throughput is identical to BF16. The 45% VRAM reduction (15 GB → 8.3 GB) is the actual benefit, enabling larger batch sizes.

FINDING E2

BF16 outperforms FP16 by 12%. H100 handles both natively via Tensor Cores, but BF16's wider exponent range avoids overflow on LLM weight distributions. For genuine INT8 throughput gains (1.5–2×), use TRT-LLM with SmoothQuant or AWQ static quantization.

PROFILE 1

GEMM dominates decode at 68.1%. nvjet decode GEMMs use bz (batch=1) tile geometry — small tiles that cannot saturate H100 tensor cores. Arithmetic intensity ~4 FLOP/byte vs H100's ~1,183 FLOP/byte crossover. Decode is firmly memory-bandwidth bound at bs=1.

PROFILE 2

Flash Attention doubles with sequence length. Attention's GPU time share grows from 4.1% (in=512) to 9.2% (in=4096). Still not the bottleneck at these lengths — but at >16K tokens it would dominate due to O(n²) KV reads.

PROFILE 3

Python dispatch is 38% of wall time. CUDA API trace: 855,648 cudaLaunchKernel × 5µs avg = 4.3 seconds of pure Python→CUDA overhead in an ~11-second decode run. Additionally, 780 cudaDeviceSynchronize × 318µs = 248ms of GPU idle time. CUDA graphs (TRT-LLM) eliminate this entirely.

TRT-LLM Build Pipeline

Step 1: QWenForCausalLM.from_hugging_face(model_path, dtype='bf16') — HF weights → TRT-LLM checkpoint (~5 min).
Step 2: trtllm-build --gemm_plugin bfloat16 --gpt_attention_plugin bfloat16 --use_paged_context_fmha enable — compiles fused TRT engine (~20 min).

Two Python import conflicts resolved: (1) torch._dynamo circular import, (2) tensorflow/protobuf version mismatch. Both fixed by import ordering in benchmarks/bench_inference.

ENGINE 1

PyTorch: lowest TTFT, highest Python overhead. Best for interactive, latency-sensitive workloads at bs=1–4. 38% of wall time is Python dispatch overhead — CUDA graphs would eliminate this.

ENGINE 2

vLLM: 2.4× higher throughput via continuous batching. PagedAttention allows more concurrent requests; continuous batching eliminates inter-batch GPU idle time. Best for batch throughput workloads. TTFT cost at low bs is the trade-off.

ENGINE 3

TRT-LLM: fused kernels + CUDA graphs eliminate Python overhead. The ~38% dispatch overhead (4.3s per decode run) that affects PyTorch is eliminated by graph capture. Combined with in-flight batching, expected to exceed vLLM throughput. Build time cost: ~25 minutes per model/dtype/TP configuration.

Summary

Six Findings

F1 · MEMORY BOUND

Decode is memory-bandwidth bound at bs=1. nvjet GEMM decode kernels use batch=1 tile geometry with ~4 FLOP/byte arithmetic intensity — far below H100's ~1,183 FLOP/byte crossover. Each decode step streams all 15 GB of model weights from HBM to produce one token. Throughput ceiling is 3.35 TB/s HBM3, not tensor core compute.

F2 · BATCHING

Batching recovers 42× throughput at bs=64. Increasing batch size from 1 to 64 recovers 42× throughput by amortizing weight-streaming costs across multiple tokens per step. This converts GEMV→GEMM, moving toward compute-bound operation. Near-linear scaling holds to bs=32.

F3 · PAGING

vLLM doubles throughput via continuous batching + PagedAttention. Peak: 8,186 vs 3,426 tok/s at bs=64 (2.39×). PagedAttention fits more concurrent requests in HBM; continuous batching eliminates inter-batch idle time. TTFT trade-off: ~750–1,600ms overhead at low batch sizes vs 12ms for PyTorch.

F4 · DISPATCH

Python dispatch is 38% of PyTorch decode wall time. 855,648 cudaLaunchKernel calls × 5µs = 4.3 seconds overhead per decode run. CUDA graphs (TRT-LLM) capture the decode step as a replayable graph, eliminating this entirely. This is TRT-LLM's primary speedup mechanism beyond vLLM.

F5 · ATTENTION

Flash Attention grows with sequence length; GEMM dominates below 8K. Attention's GPU time share doubles: 4.1% (in=512) → 9.2% (in=4096). Linear layer GEMMs (>50% of GPU time) are the bottleneck at current lengths. At >16K tokens, O(n²) attention cost would dominate.

F6 · QUANTIZATION

INT8 (bitsandbytes) saves 45% VRAM with no throughput gain. LLM.int8() dequantizes to BF16 at matrix-multiply time — no bandwidth improvement. The 45% VRAM reduction (15 GB → 8.3 GB) enables larger batch sizes. For genuine 1.5–2× throughput gains, use TRT-LLM static INT8 (SmoothQuant / AWQ).

FAQ

Frequently Asked Questions

Why is vLLM TTFT so much slower than PyTorch at bs=1? +
vLLM runs a continuous batching scheduler in Python that waits to form efficient batches before dispatching work to the GPU. At bs=1, this scheduling overhead (~750–1,600ms) dwarfs the actual inference time. The PyTorch engine skips all of this and sends the request directly to the GPU, achieving 12ms TTFT.

This is a deliberate trade-off: vLLM optimizes for throughput across many concurrent requests. For single-request interactive latency, the HF engine wins. In a real deployment, you'd route latency-sensitive traffic to a low-bs static engine and batch throughput workloads to vLLM.
Why doesn't INT8 quantization make inference faster? +
The bitsandbytes LLM.int8() method used here is post-training quantization for memory reduction, not speed. It stores weights as INT8 on disk and in GPU memory, but dequantizes them back to BF16 right before the matrix multiply. The actual GEMM runs in BF16 — same bandwidth, same TFLOPS.

For genuine throughput improvement, you need static quantization where the integer arithmetic runs end-to-end without dequantization: TensorRT-LLM with SmoothQuant, or GPTQ/AWQ models loaded via vLLM. Those can achieve 1.5–2× speedup on memory-bound decode workloads.
What is the bz suffix in the nvjet GEMM kernel names? +
The bz suffix in kernels like nvjet_tst_256x8_64x6_4x1_v_bz_TNT encodes the batch dimension tile size. bz means batch=1 — the kernel is configured for a single request's decode step.

This is the smoking gun for memory-bandwidth-bound decode: the kernel tile computes 256×8×64 = 131,072 FLOPs while loading 256×64×2 = 32,768 bytes of weights → ~4 FLOP/byte arithmetic intensity. H100's crossover to compute-bound is ~1,183 FLOP/byte, so decode at bs=1 runs at <0.4% of peak tensor TFLOPS but near peak HBM bandwidth. Increasing batch size changes bz to larger values, raising arithmetic intensity toward compute-bound territory.
Why can't you use Nsight Compute (ncu) on Rosie? +
Rosie's H100 nodes set RmProfilingAdminOnly=1, which locks hardware performance counter access to root. ncu can attach to a process but cannot read SM throughput, DRAM bandwidth, or occupancy counters — returning ERR_NVGPUCTRPERM.

The --clock-control none flag bypasses the clock-locking requirement (which also needs root on some systems), but it does not bypass the counter permission requirement. To enable per-job profiling, an HPC admin would run: 
sudo sh -c 'echo 0 > /proc/driver/nvidia/params/RmProfilingAdminOnly'
In the meantime, kernel geometry analysis from Nsight Systems SQLite output provides the memory-bound vs compute-bound determination without hardware counters.
Why did TRT-LLM take 8 job attempts to build? +
Three separate import-time conflicts compounded each other:

1. Wrong conversion API. The initial script used the low-level convert_hf_qwen() function which expected different arguments. Fixed by switching to QWenForCausalLM.from_hugging_face(model_path, dtype='bf16').

2. tensorflow/protobuf version conflict. TRT-LLM's quantization module imports AutoProcessor → image_transforms → import tensorflow. TRT-LLM downgraded protobuf to 4.24.4 but TF 2.21.0 needs 6.31.1+. Fixed by stubbing tensorflow in sys.modules before TRT-LLM imports.

3. torch._dynamo circular import. Adding the TF stub too early triggered a ValueError: tensorflow.__spec__ is None from torch._dynamo.trace_rules, which scans sys.modules at import time. Fixed by fully initializing torch._dynamo and torch._dynamo.config before adding the stub.

4. Wrong dtype flag. trtllm-build uses bfloat16/float16, not bf16/fp16. Added a case mapping in build_engine.sh.
When would Flash Attention become the bottleneck? +
At the sequence lengths benchmarked here (up to 4096 tokens), attention accounts for 4–9% of GPU kernel time — clearly secondary to linear layer GEMMs (>54%). Attention cost scales as O(n²) with sequence length, while linear layer cost scales as O(n).

The crossover point (where attention equals GEMM time) depends on the model's d_model and n_heads. For Qwen2.5-7B: attention would dominate roughly when n² × d_head > n × d_model, i.e., at seq_len > d_model/n_kv_heads × something — practically around 16K–32K tokens for a 7B model.

This is why long-context models (128K+ context) rely on techniques like sliding window attention, sparse attention, or linear attention to avoid the quadratic blowup.
How do I run a benchmark on Rosie? +
Use the generic SLURM wrapper: 
./scripts/submit_job.sh --engine pytorch -- \
    --model /home/ad.msoe.edu/boyea/InferX/models/qwen2.5-7b \

Run It Yourself

Try It

All experiments run on MSOE Rosie via SLURM. The repo is self-contained — clone it, point it at model weights, and submit. Everything below assumes you're on a Rosie login node with access to the dgxh100 partition.

1. Clone & Setup

git clone https://github.com/boyeaalhagie/InferX.git
cd InferX
mkdir -p results models

Model Weights

Qwen2.5-7B weights live at /home/ad.msoe.edu/boyea/InferX/models/qwen2.5-7b on Rosie. If running elsewhere, download via HuggingFace: huggingface-cli download Qwen/Qwen2.5-7B --local-dir models/qwen2.5-7b

2. Run a Benchmark

# PyTorch baseline — single request, 512 input tokens, 256 output
./scripts/submit_job.sh --engine pytorch -- \
    --model models/qwen2.5-7b \
    --input-tokens 512 --output-tokens 256 \
    --batch-size 1 --requests 10

# vLLM — higher throughput, batch=16
./scripts/submit_job.sh --engine vllm -- \
    --model models/qwen2.5-7b \
    --input-tokens 512 --output-tokens 256 \
    --batch-size 16 --requests 50

# Dry run — print sbatch script without submitting
./scripts/submit_job.sh --engine pytorch --dry-run -- --model models/qwen2.5-7b ...

Results land in results/ as JSONL. Each record includes TTFT, ITL, tok/s, GPU memory, and SLURM job ID.

3. Build the TRT-LLM Engine

# Build Qwen2.5-7B at BF16, single GPU (takes ~25 min)
sbatch engines/tensorrt_llm/build_engine.sh

# Custom dtype or TP size
MODEL_PATH=models/qwen2.5-7b DTYPE=fp16 TP_SIZE=1 \
    sbatch engines/tensorrt_llm/build_engine.sh

# Then benchmark with TRT-LLM
./scripts/submit_job.sh --engine tensorrt_llm -- \
    --model models/qwen2.5-7b \
    --trtllm-engine-dir results/trt_engines/qwen2.5-7b_bf16_tp1 \
    --input-tokens 512 --output-tokens 256 --batch-size 4 --requests 50

4. Profile with Nsight Systems

# Collect kernel timeline for PyTorch engine
ENGINE=pytorch INPUT_TOKENS=512 OUTPUT_TOKENS=128 \
    sbatch profiling/nsight-systems/profile_nsys.sh

# Query top kernels from the SQLite output
python3 - <<'EOF'
import sqlite3
db = 'profiling/nsight-systems/<your_profile>.sqlite'
conn = sqlite3.connect(db)
rows = conn.execute('''
  SELECT s.value, count(*), round(sum(k.end-k.start)/1e6,1) as ms
  FROM CUPTI_ACTIVITY_KIND_KERNEL k
  JOIN StringIds s ON s.id = k.demangledName
  GROUP BY s.value ORDER BY ms DESC LIMIT 10
''').fetchall()
for r in rows: print(f'{r[2]:8.1f}ms  {r[1]:6d}x  {r[0][:60]}')
EOF
