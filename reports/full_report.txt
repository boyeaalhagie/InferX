This file is generated output from the benchmark runs. Some fields are not
reliable and should not be compared across runs or engines:

1. GPU Memory Peak / GPU Utilization: the nvidia-smi poller in
   benchmarks/bench_inference queries EVERY GPU on the 8-GPU node, not just the
   assigned one. On node dh-dgxh100-2 every PyTorch run reports 67.35 GB and
   ~17-20% utilization regardless of workload. vLLM always reports ~72.7 GB
   because it pre-allocates 90% of GPU memory.

2. vLLM TTFT: the offline LLM.generate API did not return per-request metrics,
   so ttft_ms falls back to the total batch latency. It is NOT time to first
   token.

3. TensorRT-LLM TTFT: ModelRunner exposes no per-token timing, so ttft_ms is a
   placeholder (30% of total wall time), not a measurement.

Throughput (tok/s) and PyTorch TTFT/ITL are measured correctly.
See docs/ for the corrected analysis.

--- Findings ---

1. DECODE IS GEMM-DOMINATED (memory-bandwidth bound)
   The decode phase runs many small GEMM kernels: 42,672 instances at 49µs each.
   Each decode step produces one token → batch=1 matmul with shape [1 × d_model].
   These tiny GEMMs cannot saturate H100 tensor cores (designed for large tile sizes).
   This is the fundamental reason decode is memory-bandwidth limited: weights must be
   streamed from HBM for every token even though only 1×d_model of compute is done.

2. PREFILL IS COMPUTE-BOUND
   Prefill runs large GEMMs with shape [4096 × d_model]: 665µs each, fully utilizing
   tensor cores with cooperative kernel launch (coopA/coopB suffix). Flash Attention
   also scales: 457µs/call for 4096-token self-attention vs 7.6µs for 1-token decode.

3. PYTHON KERNEL DISPATCH OVERHEAD IS SIGNIFICANT
   855,648 cudaLaunchKernel calls × 5µs avg = ~4.3 seconds of pure Python→CUDA dispatch
   overhead in a ~11-second decode run (≈38% overhead). This confirms the Experiment F
   finding: eliminating this via CUDA graphs should theoretically speed up decode, but
   HF models' autograd state prevents the fast path (hence TRT-LLM uses custom graphs).

4. SYNCHRONIZATION GAPS
   780 cudaDeviceSynchronize calls @ 318µs avg = 248ms of mandatory GPU idle time per
   run. These are caused by between-step Python control flow in the HF generate() loop.
   Production runtimes pipeline decode steps to eliminate these gaps.

5. ATTENTION IS NOT THE BOTTLENECK (at this sequence length)
   Flash Attention accounts for only 2.6–5.3% of GPU time in the decode phase.
   The bottleneck is the linear layer GEMMs, not attention. At very long sequences
   (>8K), attention would become significant due to O(n²) KV reads.
